# flag-matrix

A change that reads a flag is not one happy path. It is a **matrix**: rows are **moments** (when the code reads or refreshes the value), columns are **profiles** (a set of flag values), and each **cell** has a verdict. Bugs that reach production live in the cells nobody ran: the prod combination, the moment config arrives late, the override one level up.

## Steps

1. **Catalog.** Open the repo's flag catalog: the path its AGENTS.md or CLAUDE.md names, default `docs/flags.md`. Missing: build it as [CATALOG.md](CATALOG.md) describes and commit it (asked for no commits: leave it staged and say so). Point to it with `Flags: docs/flags.md (flag-matrix skill)` in AGENTS.md, or in CLAUDE.md when only that exists; create AGENTS.md when neither does. Present: re-verify the entries the change touches against the code and fix the ones that drifted. Done when every flag the next step needs has a catalog entry whose readers are file:line you opened; a catalog built on its own is done at CATALOG.md's completion criteria.
2. **Flag map.** Look up each touched file in the catalog's Readers column: every row that lists it is a flag the change reads. Then list the flags it reads through a function it calls or that calls it. For each: its level and override order, default, value per environment, and the moments it is read (from the catalog). A touched file the catalog does not list that shows or branches on server data: find that data's source as CATALOG.md's "Derived server data" says and add the row. Done when every touched file is listed with its catalog rows or "none", and each "none" names the catalog search that found nothing.
3. **Matrix.** Write the table in the plan before running anything.
   - Profiles: everything off or default; each flag on alone, at its own level; each override (the higher level wins over the lower); the production combination; the combination of the environment where the bug was seen, or for a new feature, of every environment where the flag differs. Merge profiles the code cannot tell apart, and say which.
   - Moments: every point from the catalog's "read at" column that the change can reach, plus the error path and the value changing between two steps of one flow (created under one value, completed under another).
     - In a UI: first load, config arriving late (hold the response while the user acts: the race where a stale value overwrites newer input), a user action that refreshes config (picking a customer, project, plant), save, reopen or edit, copy or duplicate.
     - In a service: each entry point that reads the value (route, job, handler, consumer), startup and dependency wiring, a process or model cache, a runtime config reload, and the same flag read in two places through different mechanisms.
   - Assertion per cell: the behaviour the ticket asks for, plus nothing shown or changed for what the user did not touch.
   Done when every cell is planned or marked unreachable with the reason (a shared setting nobody may change, a write the environment forbids).
4. **Run.** In the repo's own test harness (none: use the platform's built-in runner at a version the repo allows, say it is the repo's first test and name the script to add): one parameterized test file (browser, API or unit test), one case per profile, the moments as steps. Set flags only through what is safe to change: local overrides, test fixtures, a mocked config response, your own test data. Shared settings (tenant, org, environment config) are read and recorded, never changed. A mock must not split the system: when the backend also reads the flag (it validates, computes or returns data from it), mocking one response gives the client one value while the server answers from another, so that cell uses real data or a local stack started with the override (an environment variable or config file for the server process); a cell that still runs on a mock is marked `mocked` and proves only the client's handling of that response. First read the environment's current values (the catalog says how) and put them in the run header: a result means nothing without the values it ran under. The matrix must go **red** on the base for the cell the change fixes; when it stays green there, an axis is missing, so add it before trusting any green. A change that introduces the flag, or adds its first reader, has no base to run: run the head with the flag off instead and show it matches the base's behaviour. The command cannot run without installing something the task did not allow: write the test, report it as not run, and name what running it needs.
5. **Report.** The table goes into the PR: rows are moments, columns are profiles, cells are PASS, FAIL with the reason, n/a, or unreachable. Unreachable cells go under "For QA" with the flag values QA needs to set. The matrix test is committed with the change, so the next change to the same code reruns it.

## Checking another environment

Any "does X work on dev / staging / prod" starts at step 3 with that environment's own values, read first. Environments differ in flags and data, so a green matrix on one says nothing about another; report which profiles that environment actually exercised, and call every path its values never reached "not verified there".
